# Localization and message ownership

These conventions apply if localization is enabled. Supported languages, default locale, locale routing, and persisted multilingual content requirements are not yet selected.

## Ownership

Keep interface messages in catalogs owned by the application or package that renders them. Maintain matching keys and interpolation placeholders across supported locales. Do not couple an independently owned package to private application message keys.

Persisted multilingual user content is data, distinct from interface translations. Define its language requirements and fallback behavior explicitly; do not silently move it into catalogs or substitute one language's content for another.

Resolve the request locale consistently with the interface. Document precedence among explicit preference, cookie, request headers, and the configured default when those mechanisms are implemented.

## Validation and errors

Shared validation schemas should emit stable message keys with interpolation parameters and field paths. Resolve them through one translation contract used by both client and server adapters. If Zod is selected, keep unrefined base schemas available when deriving create and partial-update schemas, and use the API supported by the installed version.

Choose one API message contract: localized text or keys plus parameters. When the server returns localized text, display it directly without translating it again. Keep stable machine-readable codes independent of the display language.

Verify key/placeholder parity, active-locale rendering, validation interpolation, and locale changes while a form is open.
