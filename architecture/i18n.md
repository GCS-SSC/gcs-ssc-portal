# Localization

English and French interface messages live in `app/locales/messages.ts` and `app/locales/government.ts`. Typed catalog contracts ensure French has the same keys; tests compare interpolation placeholders. `useLocale` selects the language from a same-site cookie, defaults to English, and formats dates for the active locale. The shell language control changes the interface without changing the theme or losing form data.

The root document and GC web controls receive the active language. Themes own shell copy and vendor-required-field wording; host pages own product messages. Organization names, descriptions and people’s names are user data, not translation keys. Agencies, programs, streams and calls require separately persisted `nameEn` and `nameFr`; the catalogue selects the active language without changing stored content.

Portal APIs expose stable machine-readable error codes and validation field paths. `useApiMessage` maps expected failures to safe localized text rather than displaying backend exception details. Better Auth endpoints retain their own error codes, with known account/login failures mapped by the same client adapter. The server does not translate user content or make language-specific authorization decisions.
